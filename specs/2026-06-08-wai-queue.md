# wai-queue — inter-agent task queue

> Spec for a bash-backed task queue where one orchestrator session enqueues work and one or more looping Claude worker sessions drain it, each task running in throwaway context.

## Problem

You drive one interactive Claude session (the *orchestrator*) and want to hand off chunks of work to other agents instead of doing everything inline. The obvious shape is a queue: orchestrator adds tasks, worker agents pull and execute them on a `/loop`.

The blocker is **context**. `/loop` reschedules the *same prompt back into the same session*, so context persists across iterations — it does not auto-`/clear`. A worker that does the actual task work inline accumulates the residue of every prior task; by iteration N it's dragging tasks 1…N-1, bloating context until it compacts, slows down, and loses fidelity. "How do we loop while clearing context per task?" is the question this spec answers.

A secondary blocker is correctness: multiple workers pulling from one queue can grab the same task, dead worker sessions can strand in-flight tasks forever, and dependent tasks can deadlock behind a failed dependency.

## Solution

A bash CLI, `wai-queue`, plus a thin convention for how orchestrator and worker sessions use it.

- The **orchestrator** (your interactive session) enqueues tasks and reads results by shelling out to the CLI. It holds no queue state in its own context.
- **Workers** are live Claude sessions running `/loop`. Each tick: claim the next eligible task, dispatch the *actual work to a fresh subagent*, record the result, reschedule. The work never enters the loop session's context — so "clearing context per task" is automatic, because the work was never there to clear. The loop session keeps only a one-line ack per task.
- The **queue directory on disk is the single source of truth.** Orchestrator and workers are both stateless against it. Any session can be `/clear`'d, compacted, killed, or restarted at any time and a fresh one resumes purely by reading the queue. This is what keeps the loop session's slow ack-accrual from ever mattering — when it gets heavy, wipe it; nothing is lost.

From the user's perspective: run `/queue init` once; `wai-queue add` (or `/queue add`) to enqueue; start one or more worker sessions with `/queue-worker`; watch progress with `wai-queue status`; read output with `wai-queue result <id>`.

## User stories

1. As an orchestrator, I want to enqueue a task with instructions, a target working directory, a priority, an agent type, and optional dependencies, so that I can offload bounded work and have it run in the right place by the right specialist in the right order.
2. As an orchestrator, I want each task's work to run in a throwaway subagent, so that my worker sessions never accumulate task context and never need babysitting.
3. As an operator, I want to start N worker sessions against one queue without two workers ever grabbing the same task, so that I can scale throughput by just launching more loops.
4. As an operator, I want a worker I kill mid-task to release its task back to the queue, so that a crash or `/clear` never strands work.
5. As an operator, I want a failed task to retry a few times and then dead-letter without deadlocking the tasks that depend on it, so that one failure doesn't silently freeze a pipeline.
6. As an orchestrator, I want results and failures readable on disk, so that I can triage at my leisure without a live worker running.

## Implementation decisions

### Topology

Three roles, one shared on-disk queue:

- **Orchestrator** — interactive session, enqueues + inspects. Stateless against the queue.
- **Worker(s)** — live Claude session(s) running `/loop`. Serial *internally* (one task per tick), but race-safe so any number run side by side.
- **Queue dir** — the source of truth. Default `~/.local/share/wai/queue`, overridable with `$WAI_QUEUE_DIR`. A single global queue (cross-repo by design — see `cwd` below); a second independent queue is just a second `$WAI_QUEUE_DIR`, no "named queue" machinery.

### On-disk layout

A task is a **directory**. Its status is which parent directory it currently lives under. Moving the directory between status dirs is the state transition.

```
queue/
  bin/wai-queue              # the scaffolded CLI
  pending/  <prio>-<id>/  prompt.md  meta.json
  claimed/  <id>/         prompt.md  meta.json  claim.json
  done/     <id>/         prompt.md  meta.json  result.md
  failed/   <id>/         prompt.md  meta.json  result.md   # result.md holds the failure reason
```

Claiming is `mv pending/<dir> claimed/<dir>` — atomic on a single filesystem, so two workers can never both win the same task. (Requires the queue to live on one filesystem; documented constraint.)

### Task model

- `prompt.md` — the instructions, free-form multi-line markdown (why a `.md`, not a JSON string field).
- `meta.json` — the structured bits:

```json
{ "id": "...", "cwd": "/abs/path", "priority": 50,
  "agent": "general-purpose", "needs": ["id-a", "id-b"],
  "created": "<iso8601>", "attempt": 0 }
```

`priority` is also encoded as a zero-padded filename prefix in `pending/` (e.g. `10-<id>` beats `50-<id>`) so ordering is a plain lexical `sort` with no `jq` per-entry.

### CLI surface (`wai-queue <subcommand>`)

- `init` — scaffold `bin/` + the four status dirs (idempotent).
- `add [--cwd <dir>] [--priority <n>] [--agent <type>] [--needs <id,…>] <prompt|->` — write a new task to `pending/`, print its id.
- `claim` — atomically claim the next eligible task; print its dir path; exit nonzero if none eligible.
- `complete <id> [--result-file <f>]` — move `claimed/<id>` → `done/<id>`, store result.
- `fail <id> [--reason <s>]` — bump `attempt`; retry or dead-letter + cascade (below).
- `reap` — requeue stale claims (below).
- `status` — counts per state + a per-task line (id, state, priority, attempt, blocked-by).
- `result <id>` — print a task's `result.md`.
- `cancel <id>` — remove a task (any non-running state).

### `claim()` algorithm (the heart)

1. List `pending/`, sort by priority prefix then enqueue time (FIFO within a priority).
2. For each candidate, **dep-check** against `meta.needs`: eligible iff every needed id is present in `done/`. If any needed id is in `failed/`, the candidate is dead — move it to `failed/` ("blocked by <id>") and skip.
3. First eligible candidate: `mv` it to `claimed/`, write `claim.json` (`{worker, ts}`). If the `mv` succeeds, print the path (won the race). If it fails, another worker took it — continue to the next candidate.
4. No eligible candidate → exit nonzero. The worker idles (longer reschedule).

### Worker `/loop` body (each tick)

```
wai-queue reap                                   # release stale claims first
t=$(wai-queue claim) || { backoff; reschedule }  # nonzero => idle
cd "$(jq -r .cwd "$t/meta.json")"
result = <dispatch subagent: agentType = meta.agent, prompt = prompt.md>   # throwaway context
if ok:  wai-queue complete <id> --result-file <result-tmp>
else:   wai-queue fail <id> --reason "<err>"
# reschedule; keep only a one-line ack in the loop session's own context
```

The subagent is dispatched via the session's Agent/Task mechanism with `agentType` from `meta.agent`. Its context is fresh per task and discarded on return; only its final text is captured and written straight to disk. The loop session never holds the work.

**Success/failure signal (unambiguous):** a task is `complete` iff the subagent returns a non-empty result whose first line is not the failure sentinel; otherwise the worker calls `fail`. Two failure cases collapse to one path: (a) the dispatch dies/returns null (crash, terminal error), or (b) the subagent self-reports a logical failure by emitting `FAILED: <reason>` as its first line — the task prompt instructs subagents to do this when they cannot complete the work. The worker does not judge correctness beyond this; richer verdicts are out of scope.

### Failure / retry / cascade

`fail` increments `meta.attempt`. If `attempt < N` (retry budget, configurable, default 2) → `mv` back to `pending/` for another go. If `attempt == N` → dead-letter to `failed/`, then **cascade**: walk the dependency graph and move any task whose `needs` can no longer all reach `done/` into `failed/` with reason "blocked by <id>", recursively. The queue therefore never deadlocks on a permanently dead dependency.

### Stale-claim reaper

`claim.json` carries a timestamp. `reap` moves any claim older than `$WAI_QUEUE_STALE` (default 30m) back to `pending/` with `attempt++`. This is what makes "kill a worker anytime" safe.

**Known tradeoff (explicit):** a serial worker blocked on a long subagent dispatch cannot refresh its heartbeat mid-task, so `WAI_QUEUE_STALE` must exceed the longest expected single-task duration or a still-running task can be wrongly requeued and double-run. Mitigation: generous default, bounded tasks, and the env var is tunable per deployment. Liveness detection across independent Claude sessions in bash is unreliable, so the timeout-based reaper is the deliberate v1 choice over PID/owner liveness checks.

### Packaging (markdown-only invariant preserved)

The repo ships **markdown only** — no vendored engine. Mirrors the existing `create-standards-checker` "generate on demand" pattern.

- `plugins/wai/skills/queue/SKILL.md` — the protocol: how the orchestrator enqueues, how a worker loop body is structured, the disposability/source-of-truth contract.
- `plugins/wai/commands/queue.md` — orchestrator ops (`/queue init|add|status|result|cancel`).
- `plugins/wai/commands/queue-worker.md` — starts a worker: kicks off `/loop` with the worker body above.
- `/queue init` is what writes `bin/wai-queue` and the status dirs into `$WAI_QUEUE_DIR`. The bash is a generated *user* artifact, never committed to the wai repo. No `CLAUDE.md` engine-exception change required.

## Testing decisions

Pure-bash tests, deterministic, no model required — alongside the existing `plugins/wai/scripts/tests/` style.

- **Atomic claim race** — launch two `wai-queue claim` in parallel against a 1-task queue; assert exactly one wins and the other exits nonzero. Extend to N workers / M tasks; assert a partition (every task claimed once, none twice).
- **DAG ordering** — enqueue with `--needs`; assert a dependent is never claimable until its deps are in `done/`; assert priority-then-FIFO order among eligible tasks.
- **Cascade-fail** — fail a task past its retry budget; assert it dead-letters and that its transitive dependents move to `failed/` with "blocked by" reasons, with no survivors left stuck in `pending/`.
- **Retry budget** — fail a task `attempt < N` times; assert it returns to `pending/` each time and dead-letters exactly on the Nth.
- **Reaper** — write a `claimed/` task with an old `claim.json` ts; run `reap`; assert it returns to `pending/` with `attempt++`; assert a fresh claim is left untouched.

The subagent dispatch is **stubbed** in tests: a fake stands in for the real Agent/`claude` call so completion/failure paths are exercised without invoking a model. Prior art: the smoke tests under `plugins/wai/scripts/tests/`.

## Out of scope

- **No `claude -p` headless worker variant.** The worker is a live `/loop` Claude session dispatching subagents, by decision. A pure-bash + headless-`claude` drain loop is explicitly not built here.
- **No inline / self-`/clear` worker.** Work always runs in a throwaway subagent, never in the loop session with periodic clears.
- **No named-queue registry.** One queue per `$WAI_QUEUE_DIR`; multiple queues = multiple env values.
- **No cross-filesystem queue.** Atomicity relies on `mv` within one filesystem.
- **No live push notifications to the orchestrator.** Results are read on demand (`status` / `result`); no event stream or webhook.
- **No web UI / dashboard.** `status` is text. (Diffscape is the repo's only UI feature; not extended here.)
- **No second engine exception in the wai repo.** Nothing engine-backed is vendored; the CLI is scaffolded into the user's environment.
- **No PID/owner liveness detection** for stale claims — timeout-based reaping only.

## Further notes

- **The context-clearing answer, in one line:** the work lives in a per-task subagent whose context dies on return, the loop session holds only thin acks, and the disk queue is the source of truth — so the loop session is disposable and can be wiped or restarted whenever it gets heavy.
- **Throughput knob** is just "how many worker sessions you start." Each is serial; parallelism is across sessions, made safe by atomic directory claims.
- **Cross-repo by design:** a task's `cwd` lets one global queue serve many projects; the worker `cd`s before dispatching.
- Default tunables to surface in the skill docs: `$WAI_QUEUE_DIR` (location), `$WAI_QUEUE_STALE` (reaper timeout, default 30m), retry budget `N` (default 2).
